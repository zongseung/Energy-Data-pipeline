# ASOS 일사량(solar_radiation) 관측 지점 목록

Task 7(ASOS 일사량 수집 재개 + 과거 백필)에서 실제 기상청 API 응답으로 확인한
내용. Task 5(데이터 카탈로그)가 이 문서를 참고한다.

## API 필드

- 엔드포인트: `AsosHourlyInfoService/getWthrDataList` (기존과 동일, 별도 엔드포인트 아님)
- 일사량 키: **`icsr`** (응답 JSON의 item 딕셔너리 키, 모든 지점/시각에 항상 존재하는
  키이며 미관측/야간에는 빈 문자열 `""`)
- 단위: **MJ/m²** (해당 정시 관측 1시간 구간의 일사량 누적치로 추정 — 기상청
  지상기상관측지침에 일사량 항목 자체의 시각 라벨 명시 문구는 없음. 강수량·일조시간
  항목의 "구간종료 라벨" 서술에서 유추한 **추정**이며, `fetch_data/weather/database.py`
  `WeatherASOS.solar_radiation` 컬럼 코멘트에도 동일하게 "추정"으로 표시되어 있다.
  Task 7에서 KMA 공식 문서로 명확한 근거를 재확인하려 했으나(2026-08-11 시도), 검색·PDF
  조회로는 확정 문구를 찾지 못해 추정 표시를 그대로 유지한다.)
- 검증 근거: 2025-07-01 서울(108) 시간자료 실측 — 00~05시·21~23시(야간) `icsr` 빈 문자열,
  06~20시(주간) 0.02~2.83 사이 값으로 일출·일몰 패턴과 일치.

## 미관측 처리 방식

1. **수집 단계** (`fetch_data/weather/asos_collect.py::normalize_weather_data`):
   `icsr`이 빈 문자열이면 `pd.to_numeric(errors="coerce")`로 `NaN`이 된다. `icsr`
   컬럼 자체가 없는 입력(일사량 도입 이전 호출부·테스트)도 방어적으로 `NaN`으로
   채운다 — 어느 쪽이든 예외 없이 처리된다.
2. **적재 단계** (`fetch_data/weather/database.py::load_asos_df`): `NaN`은 명시적으로
   `None`으로 변환되어 DB에 SQL `NULL`로 들어간다(부동소수점 NaN 리터럴 아님).
3. **UPSERT 충돌 시** (COALESCE): 들어오는 값이 `NULL`이어도 이미 채워진
   `solar_radiation`을 지우지 않는다 — 매일 도는 daily flow가 (icsr을 못 가져온
   과거 방식이든, 실제로 미관측 지점이든) `NULL`을 보내도 백필로 채운 값이나
   기존 관측값이 살아남는다. 실제 DB(로컬 pv, localhost:5436)에서 2025-07-01
   서울/강화 데이터로 이 동작을 직접 검증했다(Task 7 리포트 §검증 참고).

## 참고: 과거 CSV의 "43개 지점, 2019-01" 데이터 출처

`data/asos_all_merged.csv`에 남아있는 2019-01 구간의 solar radiation 값은 이
저장소의 현재 수집기가 만든 게 아니다. 최초 커밋(`34e6613`) 시점의
`collect_asos.py`는 정확히 이 43개 지점 하드코딩 리스트를 갖고 있었지만, 이미
`df = df[["tm", "hm", "ta", "stnNm"]]`로 `icsr`을 걸러낸 채 저장했다 — 즉 그
43-지점 리스트 자체는 이 저장소 역사와 일치하지만, 실제 solar radiation 값이
채워진 2019-01 CSV는 이 저장소 밖에서 별도로(또는 그 이전 버전 코드로) 생성되어
병합된 것으로 보인다. 현재는 95개 지점(`config/station_list.csv`) 전체를
수집하며, 그중 63개가 일사를 관측한다.
