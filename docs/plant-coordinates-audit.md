## 1. 소스 확인

좌표 하드코딩은 정확히 두 군데다. 셋째 후보로 지목된 `scripts/migrations/schema_migration.py`는
좌표를 **만들지 않는다** — `p2()`가 `nambu_plants`/`namdong_plants` 테이블(둘 다 `pv_test/init_db.py`가
CSV·지오코딩으로 채운 결과)을 조인하고, `namdong_plants`에 값이 없을 때만
`fetch_data.pv.database.get_namdong_location()`(=`database.py`의 사전)으로 폴백한다. 즉 지금
`plants.lat/lon`에 들어있는 값은 **전부 이 두 소스 중 하나에서 왔다.**

- `fetch_data/pv/database.py:145-190` — `NAMDONG_PLANT_LOCATIONS` (남동 11개 발전소명 → 좌표, 하드코딩)
- `pv_test/init_db.py:50-72` — `PLANT_COORDS` (남동 11개 + 남부 지역 8개 도시명 → 좌표, 하드코딩).
  이 파일의 `geocode_address()`가 **1순위로 이 하드코딩을 문자열 부분매칭**하고, 실패하면 Kakao→Nominatim
  API를 부른다. 남동 11개 발전소는 전부 이름이 정확히 일치해 하드코딩 값이 그대로 들어갔다
  (Kakao/Nominatim 호출 없음) — `plants` 현재 값과 대조해 확인.

**코드 하드코딩 소스는 이 둘뿐이지만, 판정 근거로는 세 번째 출처를 추가했다** — 공공데이터포털
15147894 `한국남부발전(주)_태양광발전소 위치 정보_20250827`(발전소명·호기·위도·경도, 22행,
남부발전 자체 공시). 이건 좌표를 만드는 코드 소스가 아니라 §4에서 "어느 쪽이 맞는지" 판정할 때
쓴 1차 출처(§2 근거우선순위 3번)다.

## 2. 판정 방법

1. **행정구역 범위** — 발전소명의 지명이 좌표의 실제 행정구역과 맞는지 (역지오코딩 대신 OSM
   Nominatim으로 대상 주소를 지오코딩해 거리 비교. 새 의존성 추가 없음 — 1회성 웹 조회).
2. **같은 사이트 다른 설비 주소** — `plants`에서 같은 이름 계열의 비-태양광 설비(예: `영흥_4` 화력,
   `삼천포해양소수력_1`)가 주소를 갖고 있으면 그 좌표와 대조. **가장 강한 근거.**
3. **발전사 공시자료** — 공공데이터포털의 발전사 공식 공시 데이터셋(예: 15147894 `한국남부발전(주)_
   태양광발전소 위치 정보`, 발전소명·호기·위도·경도 22행), 각 발전본부(신인천/부산/남제주/삼척)의
   공식 주소, `(주)탑선`의 자체 실적 목록, 남동발전 보도자료(고흥만 수상태양광) 등. 출처는 표마다 명시.
4. 위 어느 것도 없으면 **미확정**으로 남긴다.

거리는 모두 haversine으로 계산했다(파이썬 표준 `math`만 사용, 신규 의존성 없음). 주소·지명 좌표는
OSM Nominatim으로 지오코딩했고, **1차 판정 이후 리뷰에서 "도로 중심점/도시 대표좌표를 부지로
오인"한 사례가 다수 지적돼**, 가능한 곳은 실제 시설 POI(예: "HSD엔진", "신인천복합화력발전소" 같은
건물/사업장 태그)로 교차검증했다 — 자세한 내용은 §10.

## 4. 부수 발견 — 좌표는 있지만 자기 주소와 어긋나는 남부발전 3기

태양광 45기 중 `address`가 채워진 건 3기뿐이다(부산신항태양광, 부산역 선상 주차장,
이천D(백사면B) 태양광). **셋 다 좌표가 자기 주소와 크게 어긋난다.** 원인은
`pv_test/init_db.py`의 `geocode_address()`가 **주소로 지오코딩하기 전에 발전소명을 하드코딩
사전에 부분 문자열로 먼저 매칭**하기 때문이다(`normalize_plant_name(key) in base_name` 검사).
"부산신항태양광"이라는 이름에 "부산"이 부분 문자열로 들어있어 `PLANT_COORDS["부산"]`
(=부산시청 좌표)이 실제 주소 지오코딩보다 먼저 채택됐다.

**리뷰 반영**: 1차 판정에서는 실제 주소를 Nominatim으로 직접 지오코딩한 값을 썼는데, 리뷰에서
"공공데이터포털에 남부발전이 낸 공식 위치 공시가 있는지부터 확인했어야 한다"는 지적을 받았다.
확인해보니 있었다 — **15147894 `한국남부발전(주)_태양광발전소 위치 정보_20250827`**
(발전소명·호기·위도·경도, 22행, `data.go.kr/data/15147894`). 이 3기 모두 이름이 그대로 매칭돼
(`부산 신항 태양광`, `부산역 선상주차장 태양광`, `백사면B 태양광`) **1차 출처(§2 근거우선순위
3번)로 격상, 공식 공시 값으로 교체**했다. 부산역은 1차 Nominatim값과 사실상 동일해 교차검증됐고,
부산신항·이천D는 값이 바뀌었다(부산신항 3.4km, 이천D 1.3km — 방향은 같아 결론은 안 바뀜).

## 6. 미확정으로 남긴 것

**`율치태양광` (plant_id=143) 1기뿐이다.** "영암"과 짝지어 수집되는 이름이라 인근일 개연성은
있으나, place-name으로도 공시자료로도 위치를 특정할 근거를 찾지 못했다. 추측으로 채우지 않고
`lat/lon = NULL`로 남긴다. (참고: `fetch_data/pv/ekr_collect.py`는 발전량만 수집하고
좌표/주소 정보를 다루지 않으므로 수집기 코드에도 단서가 없다.)

## 7. 수집기 좌표 소스 통합 제안 (이 태스크에서는 실행하지 않음)

이번 조사로 확인된 구조적 문제. **코드는 건드리지 않았다** — 다음은 제안이다.

1. **SSOT 부재.** 좌표가 `fetch_data/pv/database.py`(하드코딩 dict)와 `pv_test/init_db.py`
   (하드코딩 dict + 지오코딩)에 중복 정의돼 있고, 서로 다른 값을 갖는다(§3). `plants` 테이블 자체를
   좌표 SSOT로 승격하고, 두 수집기가 이 테이블에서 조회하도록 리팩터링을 제안한다.
2. **부분 문자열 매칭 버그.** `pv_test/init_db.py:geocode_address()`와
   `fetch_data/pv/database.py:get_namdong_location()` 둘 다 발전소명에 사전 키가
   **부분 문자열로만** 포함되면 매칭된다(`if key in plant_name`). "부산"이 "부산신항태양광"에
   부분 매칭되어 실제 주소를 두고 도시 대표좌표를 쓴 것이 §4의 근본 원인이다. 정확히 일치하는
   키가 없으면 지오코딩을 우선하도록 순서를 바꿔야 한다.
3. **매칭 실패 시 무언(silent) 폴백.** `get_namdong_location()`은 매칭 실패 시 **서울시청 좌표**로,
   `geocode_address()`는 **한국 중심 좌표**(35.9078/127.7669)로 조용히 폴백한다(§4의
   `이천D(백사면B) 태양광`이 실제로 이 경로를 탔다). 폴백 대신 `NULL` + 경고 로그로 바꿔야
   틀린 값이 "확실"로 둔갑하는 사고(§4)가 재발하지 않는다.
4. **`capacity_confidence`의 의미 과다 사용.** `schema_migration.py`가 이 컬럼을 "좌표 존재 여부"로도
   쓰고 있는데(§4), 좌표 신뢰도와 용량 신뢰도는 다른 축이다. 좌표 전용 신뢰도 컬럼을 별도로 두는
   편이 낫다.

## 9. 셀프 리뷰

- **완전성**: 태양광 45기 전부를 다뤘다 — 남동 23기 두 소스 전수비교(§3), 남부 좌표보유 3기의
  자체 주소 대조(§4), 좌표 전무 19기의 보완 시도(§5).
- **정직성**: 근거 없이 판정하지 않았다 — `율치태양광`은 웹 조회로도 위치를 특정하지 못해
  미확정으로 남겼다. `고흥만 수상태양광`·`영암` 3기는 리/읍 단위 근사임을 명시했다(정밀 지번
  아님).
- **되돌림 가능**: SQL은 `plant_id`를 명시하고, 모든 `UPDATE`에 이전 값을 주석으로 남겼다.
- **절제**: 산출물은 이 문서와 `sql/fix_plant_coordinates.sql` 2개뿐이다. 수집기 코드는
  수정하지 않았다(§7은 제안일 뿐). 지오코딩 파이프라인을 만들지 않고 웹 조회 1회성 호출로
  마쳤다(신규 의존성 없음).
- **우려사항**: (1) 영동·탑선·고흥만·신규 채움 18기는 전부 "근사"~"확정에 가까움" 신뢰도다 —
  정확한 지번 지오코딩이 아니라 행정구역/부지 POI 중심점이다. ASOS 조인에는 충분하지만 그 이상의
  정밀도가 필요하면 재작업이 필요하다. (2) "영암1차/영암2차"가 실제로 삼호읍 용앙리 사업의
  1·2단계인지는 완전히 확인하지 못했다 — 셋 다 우선 동일 좌표로 채웠고, `140`(합계행)이 `141`/
  `142`와 물리적으로 겹칠 위험을 SQL 주석에 남겼다. (3) §7 제안은 이번 태스크 범위 밖이며 별도
  태스크로 진행해야 한다. (4) 탑선의 판정 근거는 "㈜탑선 사업장 소재지"이지 "이 발전소의 실제
  설치 부지" 확증은 아니다 — `database.py` 배제는 확정이나 정밀 부지는 미확정으로 남긴다.
