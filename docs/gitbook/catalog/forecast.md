# 기상 예보

기상청 동네예보 3종입니다. 예보라서 **관측이 아닙니다.** "실제로 어땠나"는 [기상 관측](weather.md)을 쓰세요.

{% hint style="danger" %}
**이 페이지의 시각은 UTC입니다.** 발전량·수요·SMP·관측 같은 다른 자료는 모두 한국 시간(KST)인데 예보만 다릅니다. 다른 자료와 붙이려면 **9시간을 더해야** 합니다. 이 데이터에서 가장 자주 틀리는 부분이니 아래 "시각이 UTC입니다"를 먼저 읽으세요.
{% endhint %}

## 한눈에

예보 자료는 DB 테이블이 아니라 **NAS의 CSV 파일**에 있습니다. 조회 함수가 필요한 파일만 읽어 옵니다.

| 예보종 | 내용 | 앞으로 얼마나 | 수집된 지역 |
| --- | --- | --- | --- |
| `단기예보` | 3일치 동네예보 | +6 ~ +67시간 | 18개 시도 |
| `초단기예보` | 6시간 이내 예보 | +1 ~ +6시간 | 7개 시도 |
| `초단기실황` | 관측 실황 (예보가 아니라 현재 관측값) | 없음 | 10개 시도 |

* 확인한 지역(필동, 방배3동 등)은 2023년 자료부터 있습니다. 모든 지역과 예보종의 전체 기간은 아니며, 실제로 있는 월은 아래 함수로 확인합니다.
* 예보종마다 수집된 지역이 다릅니다. 결과가 비면 지역을 틀린 것이 아니라 그 예보종에 없는 지역일 수 있습니다.
* NAS에 없는 월은 [기상 예보 수집 요청](forecast-collect.md)에서 요청해 채울 수 있습니다.

## 이런 질문에 씁니다

* 서울특별시 종로구 단기예보 데이터가 있는지 확인해 줘.
* 개포1동의 2023년 1월 단기예보 1시간기온을 보여줘.
* 필동의 2023년 1월 단기예보에서 1시간기온 월별 평균을 알려줘.
* 서울 강남구에 있는 단기예보 요소가 뭐가 있어?

시군구만 말해도 됩니다. 존재 여부는 시군구까지만 알면 바로 확인하고, 실제 값은 읍면동·요소·기간을 알려 주면 바로 조회합니다. 빠진 조건은 LibreChat이 되묻습니다.

## 지역과 요소

**지역**은 시도 → 시군구 → 읍면동 순서입니다. 지역 목록은 NAS의 폴더 이름을 읽은 것이라, 목록에 있다고 해서 월별 예보값 파일이 있다는 뜻은 아닙니다.

**요소**는 예보종마다 다릅니다. 이름도 다릅니다. 단기예보의 `1시간기온`이 초단기실황에서는 `기온`입니다.

| 예보종 | 요소 |
| --- | --- |
| `단기예보` (12종) | `1시간기온` `습도` `풍속` `하늘상태` `강수확률` `1시간강수량` `1시간적설` `강수형태` `일최고기온` `일최저기온` `동서바람성분` `남북바람성분` |
| `초단기실황` (6종) | `기온` `습도` `풍속` `풍향` `강수` `강수형태` |

## 조회에 쓰는 함수

LibreChat이 아래 함수를 이용해 SQL을 만들고, 답변에 사용한 SQL을 함께 보여 줍니다. 이런 모양입니다.

| 함수 | 하는 일 | 입력 |
| --- | --- | --- |
| `forecast_regions` | 지역 목록 | 예보종, (시도), (시군구). 입력을 줄이면 위 단계 목록이 나옵니다 |
| `forecast_elements` | 요소 목록 | 예보종 |
| `forecast_months` | 실제 자료가 있는 월 목록 | 예보종, 시도, 시군구, 읍면동, 요소 |
| `forecast` | 예보값 | 예보종, 읍면동, 요소, 시작월, 종료월, 시도, 시군구 |

```sql
SELECT *
FROM research.forecast(
    '단기예보', '개포1동', '1시간기온', '202301', '202301',
    sido_filter => '서울특별시', sigungu_filter => '강남구'
);
```

`forecast`의 두 번째 입력은 시군구가 아니라 **읍면동**입니다. 시작월과 종료월은 `YYYYMM` 형식이고 둘 다 포함합니다. 같은 이름의 읍면동이 있을 수 있어서 시도와 시군구도 함께 지정합니다.

## 결과 컬럼

| 컬럼 | 뜻 |
| --- | --- |
| `sido`, `sigungu`, `dong_name`, `element_name` | 지역과 요소 |
| `grid` | 기상청 격자 번호 (예: `61_125`) |
| `base_at` | **발표 시각** (UTC) |
| `lead_hours` | 발표 후 몇 시간 뒤의 예보인지. 초단기실황은 비어 있음 |
| `target_at` | **예보 대상 시각** (UTC). `base_at` + `lead_hours` |
| `value` | 값. 요소마다 단위가 다릅니다 (기온 ℃, 습도 %, 풍속 m/s). 하늘상태와 강수형태는 코드값입니다 |

같은 시각의 예보가 발표 시각마다 여러 번 나옵니다. 가장 정확한 예보를 원하면 `target_at`이 같은 행 중 `base_at`이 가장 늦은 것을 고르세요. 그것이 대상 시각에 가장 가깝게 낸 예보입니다.

## 꼭 알아두세요

### 시각이 UTC입니다

기상청이 동네예보 자료를 협정세계시(UTC, 한국 시간보다 9시간 느림)로 제공합니다. 함수는 이 값을 **그대로** 돌려주고 보정하지 않습니다.

* 발전량·수요와 붙이려면 9시간을 더하세요.
* 보정하지 않으면 하루 최고기온이 07시, 최저기온이 20시쯤 찍힙니다. 이런 모양이면 시차를 안 맞춘 것입니다.
* 초단기실황 기온이 한겨울 새벽에 시간당 1~2℃씩 오르면 자료가 이상한 것이 아니라 시차 때문입니다. 실제로는 늦은 오전의 값입니다.

<details>

<summary>관측(ASOS)과 비교할 때는 10시간이 더 잘 맞았습니다</summary>

예보 자료를 관측 자료인 `weather_asos`와 시각 단위로 비교하면 이론대로 9시간이 아니라 **10시간**에서 가장 잘 맞습니다. 리드타임이 없는 초단기실황 기온으로 재 보면 10시간에서 평균 절대오차가 0.16℃이고 9시간에서는 0.68℃입니다(2024년 1월·6월 동일). 관측 쪽 시각이 1시간 밀려 있을 가능성이 있지만 아직 확인하지 못했습니다. 관측과 시각 단위로 비교하는 분석이라면 시차를 직접 재고 시작하세요. 발전량·수요와 붙일 때는 9시간이 맞습니다.

</details>

### 같은 예보가 두 번씩 나옵니다

원본 파일에 같은 기간이 두 벌 들어 있어 행이 약 두 배입니다. 합계나 평균을 그냥 내면 이중으로 계산되니 `SELECT DISTINCT`로 먼저 겹친 행을 접으세요.

### 매달 1일은 값이 겹칠 수 있습니다

월 파일이 다음 달 1일까지 담고 있는데 함수가 파일의 연·월 하나로 모든 행에 날짜를 붙입니다. 그래서 2월 1일 예보가 1월 1일에 겹쳐 보일 수 있습니다. 1일에만 값이 두 갈래로 갈리면 이 때문이니, 엄밀한 분석에서는 매달 1일을 빼세요.

### 기간을 꼭 정하세요

기간을 생략하면 30개월치를 통째로 읽습니다. 파일이 400개를 넘으면 함수가 거부합니다. 질문에 시작월과 종료월을 적어 주세요.

### 평균·합계도 물을 수 있습니다

서버가 확인한 `forecast` 조회를 그대로 두고 그 위에서 집계합니다. 원하는 기간과 집계 단위(월별, 일별 등)를 질문에 적으면 됩니다.
