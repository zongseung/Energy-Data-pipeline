## 응답 포맷이 특이하다 — `<item>` 래퍼가 없다

레코드마다 **별도 `<items>` 태그**로 온다. 흔한 `<items><item>…</item></items>` 가 아니다.

```xml
<body>
  <items><ymd>2026-08-03</ymd><gencd>997D</gencd>…</items>
  <items><ymd>2026-08-02</ymd><gencd>997D</gencd>…</items>
  …
```

**`root.findall(".//items")` 로 받아야 한다.** `find()` 를 쓰면 첫 하나(최신일)만 잡힌다.

### ⚠️ 수집기에 이 버그가 있다 (2026-09-10 발견, 미수정)

```python
# nambu_backfill.py:114 · nambu_collect.py:102
items_node = root.find(".//items")            # ← 첫 하나만
return [{child.tag: child.text for child in items_node}]
```

실증 — `997D` 로 8/1~8/7 요청:

```
현재 수집기  -> 1건   ['2026-08-07']
findall 로  -> 7건   ['2026-08-07' … '2026-08-01']
```

**영향**: 백필이 하루씩(`strSdate == strEdate`) 도는 정상 경로는 멀쩡하다 — 그래서 커버리지
93.6% 가 나온다. 문제는 두 곳이다.
① `nambu_backfill.py:199` 의 보정 경로가 `(d, d+1)` 로 부르는데, 첫 `<items>` = **최신일**이라
   원하던 `d` 가 아니라 `d+1` 을 받아온다.
② 범위 요청을 못 쓴다. 고치면 **한 달치를 1콜**로 받아 백필이 30배 빨라진다.

고침은 한 줄이다.

```python
nodes = root.findall(".//items")
if nodes:
    return [{c.tag: c.text for c in n} for n in nodes]
```

포맷 1(`<item>` 있음)은 위에서 먼저 반환하므로 충돌하지 않는다.

## 원천 공백 — 재확인 완료 (고친 파서로)

`plant_id 3`(`997D`) 기준. **파서를 고쳐 전 범위를 받아 확인했다.**

| 구간 | 확보 | 기대 |
|---|---|---|
| 2020-09-01 ~ 10-05 | **1일** (09-01) | 35 |
| 2020-12-29 ~ 2021-03-29 | **0일** | 91 |
| 2021-09-24 ~ 10-31 | **1일** (10-05) | 38 |
| 2026-08 (대조군) | **31일** | 31 |

대조군이 31/31 로 다 오므로 파서 문제가 아니다. **원천에 없는 게 맞다.**
남부 태양광 18계열 합계 60,410 빈시간은 API 로 못 채운다.
→ 파일데이터(발전소별 태양광 실적 23종)에 있는지 확인하는 것이 남은 길이다.

## 우리 스키마 매핑

```
gencd   -> plants.code
hogi    -> plants.unit_no
ipptnm  -> plants.plant_name       "한국남부발전(주)_XXX 태양광발전실적" 원문 그대로
        -> plants.operator = 'nambu', fuel_type = 'solar'
ymd + qhorgen01..24 -> generation(timestamp, plant_id, gen_kwh, source='api')
```

## 미확인

- `_GW` 본(15125318)과 이 API 가 같은 것인지, 응답이 다른지
- `qvodtimemax`/`qvodtimemin` 의 정의 (최대·최소가 난 시각인지 값인지)
- `gen_kwh` 단위가 kWh 로 확정인지 (다른 계열과 대조 안 함)
