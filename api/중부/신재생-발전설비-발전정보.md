## 실측으로 알아낸 것

### 1회 호출 = 2일치다

`DAILY` 로 부르면 **조회일 + 다음날** 이 온다. `dataTerm` 을 바꿔도 같다.
그래서 `collect.py` 는 2일씩 건너뛰며 훑고 `--budget` 으로 쿼터를 끊는다.

### `resultCode=02` 는 "그 날짜에 데이터가 없다"는 뜻이다

"데이터베이스 에러" 라고 오지만 **쿼터와 무관하다.** HTTP 200 에 `<item>` 0건으로 오므로
resultCode 를 안 보면 "데이터 없음" 과 구분이 안 된다. 실패로 세면 구멍마다 멈춘다 —
2026-09-09 에 이걸로 720회에서 헛멈췄다. 지금은 빈 리스트를 돌려주고, 진짜 오류
(22 요청제한 초과 등)만 올리며 연속 10회면 중단한다.

데이터 하한은 **2018-11-15**. 11-01~13 은 02 다.

### 전 본부 공통 결손

`2022-09-19 ~ 10-19` **29일**이 5개 본부 전부 비어 있다. 하루짜리 산발 결손
(2025-06-26 · 07-17 · 07-21 · 08-14 · 08-20 …)도 전 본부 공통이다. **재시도해도 안 온다.**

### `daypower` 는 발전량이고 단위는 kWh다

호기 단위로 1:1 대조되는 **소수력**(공식 [15139102](https://www.data.go.kr/data/15139102/fileData.do))
으로 일 합계를 맞췄다 — 보령 1호기 **0.983** · 2호기 **0.992** · 신보령 1호기 0.935.
설비별 평균이 설비용량 대비 합리적이고, 태양광이 정상 일사곡선을 그린다
(제주대 태양광 06~19시, 12시 피크).

**시각이 구간시작인지 구간종료인지는 미확정이다.** 시간별 공식 자료가 상명풍력
([15119454](https://www.data.go.kr/data/15119454/fileData.do))뿐인데 그건 **송전량**이라
대조가 성립하지 않는다(최선이 상관 0.637). 일별 합계는 맞으니 **일 단위 분석은 안전**하고,
시간대별 분포는 ±1시간 불확실하게 다룬다. `v_generation_hourly` 에 중부 보정은 넣지 않았다.

## 적재 시 교정 (`load.py`)

| 규칙 | 규모 |
|---|---|
| 전구간 0 설비 제외 | 2개 설비 37,239행 (세종 매봉산풍력 · 신보령 태양광 2호기) |
| 이름 분절 합침 | 보령 수상태양광(공백 표기 두 번 변경) · 인천 연료전지 호기→단계 |
| 스파이크 → NULL | 112행 (설비 p99 의 3배 초과) |
| 태양광 야간 >0 → NULL | 20행 (21~04시) |

적재 결과 **28계열 1,287,155행** (2018-11-15 ~ 2026-09-01).

## 수집 잔여

세종 `2021-03-18 ~ 2024-12-31`(1,385일, ~693회) · 인천 `2024-05-13 ~ 2025-01-01`(232일).

```bash
uv run python -m pipeline.fetch_data.komipo.collect --station 9830 --budget 950 --start 20210318 --end 20241231
```

**`--station` 을 꼭 쓸 것.** 없으면 STATIONS 순서로 훑으며 보령·인천의 02 구멍을
매 실행 재요청해 ~240회(25%)를 버린다.
